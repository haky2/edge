## R — 리밸런싱 트리거

### 목적
포트폴리오 진단(`/portfolio-review`)은 요청 시점의 구조 해석만 준다. R은 **"점검할 때가 됐다"를 백엔드가 먼저 알리는** 장치: 비중 드리프트·상단권 쏠림·매크로 공통 노출 급증을 룰로 감지해 Slack 신호를 보낸다. 매매 지시가 아니라 **점검 신호** — 문구에 고정 명시.

### 설계

**포지션 스냅샷 영속 (전제 인프라)**
백엔드는 무상태(positions는 쿼리 파라미터) → 스케줄 잡이 평가할 포지션이 없다. 해결: `/portfolio-review` 호출 시 positions를 `{DATA_DIR}/portfolio_snapshot.json`에 저장(단일 사용자 전제 — premortem.json 전례). 앱이 내 자산 탭을 열 때마다 자동 최신화되는 구조라 별도 동기화 UI 불필요.
- 스냅샷: `{positions: {code: {avg, qty}}, updatedAt}`
- **기준점(baseline)**: 드리프트 비교 대상. `POST /rebalance/baseline` — 현재 스냅샷을 기준점으로 복사(+당시 평가 비중 함께 저장 — 비중은 가격 의존이라 시점 고정 필요). 최초엔 첫 스냅샷이 자동 baseline.

**트리거 룰 (전부 계산, LLM 0, 임계값은 env로 조정 가능)**
1. **종목 비중 드리프트**: 현재 평가 비중 vs baseline 평가 비중, |Δ| ≥ 7%p (`REBALANCE_DRIFT_PP`, 기본 7). 가격 변동만으로도 발생 — 그게 정상(리밸런싱의 정의).
2. **상단권 쏠림**: 밸류 밴드 상단권(위치 ≥80%) 종목들의 합산 비중 ≥ 40% (`REBALANCE_TOP_BAND_PCT`). "고평가 단정"이 아니라 "차익 실현 점검" 신호 — P2 규칙(상단권=고평가 단정 금지)과 동일 프레임 유지.
3. **매크로 공통 노출 급증** (v2, 옵션): PortfolioReviewService의 노출 계산 재사용, 최대 절대 노출이 baseline 대비 +0.15 이상 증가. v1에선 빼고 시작(룰 1·2로 충분한지 먼저 관찰).

**발동 → 알림**
- signals-scan(18:00)에 신호 7종째로 통합. 스냅샷 `updatedAt`이 **3거래일 이내일 때만 평가**(낡은 포지션 오발동 방지 — 앱을 안 열면 침묵).
- 쿨다운: 룰별 14일 (`signal_state.json` 디듀프 패턴 재사용, 키 `RB:룰:종목`).
- Slack ⚖️ 섹션: "비중 점검 신호: 삼성전자 32%→41% (기준 대비 +9%p)" + "매매 지시 아님, 포트폴리오 점검 신호" 고정 문구.

### 슬라이스
- **✅ R1 (Fable, 커밋 34f5228)** — 스냅샷/기준점 영속 + `RebalanceService.check()`(룰 1·2) + RebalanceTest 11 + `GET /rebalance-check`·`POST /rebalance/baseline`. curl 검증 완료(룰2 실발동·드리프트 시뮬·기준점 재설정).
- **R2 (Sonnet)** — signals-scan 통합(신선도 게이트·쿨다운·⚖️ 포맷). 수동 트리거 검증.
- **R3 (Sonnet)** — 앱: 포트폴리오 진단 카드에 드리프트 행(현재 vs 기준 비중, 발동 룰 배지) + "기준점 재설정" 버튼(`POST /rebalance/baseline`). iOS+Android 동시.

### 테스트
드리프트 계산(비중 산출·Δ%p)·상단권 합산·신선도 게이트·쿨다운·baseline 없음(첫 실행) 각 유닛. 엣지: 포지션 1종목(비중 100% 고정 — 드리프트 정의 불가, 룰 1 skip), qty 0, baseline에만 있는 종목(전량 매도 = 드리프트로 취급).

### 리스크·한계
- 단일 사용자 전제(스냅샷 파일 1개). 멀티유저 확장 시 사용자 키 분리 — v1 범위 밖(premortem과 동일).
- 계좌별 리밸런싱(ISA만 따로 등)은 G3 그룹 뷰 이후 v2 — v1은 전체 합산 기준.
- 임계값 7%p·40%는 초기값일 뿐 — 튜닝은 몇 주 관찰 후(과최적화 금지 원칙).

## D — 지켜볼 후보 발굴

### 목적
"어느 종목을 새로 지켜봐라"에 답한다. 현재 앱은 관심종목 11개 폐쇄형 — 관심 밖에서 신호가 켜진 종목을 볼 방법이 없다. **유니버스는 전시장이 아니라 관심 섹터의 peer 바스켓**(PeerValuationService.SECTOR_PEERS 재사용, ~30종목) — KIS 호출량·소음 관리 + "내 투자 문법 안의 후보"라는 명확한 프레임. 카드에 "관심 섹터 내 후보" 고정 표기.

### 설계

**유니버스**: SECTOR_PEERS 전 바스켓 합집합 − 현재 관심종목 = 후보 풀(±20종목).

**신호 4종 (전부 기존 인프라 재사용, LLM 0)**
1. **수급 전환**: F4 `detectReversal` 재사용 (외인/기관, 5일 연속 반대 후 전환)
2. **상대 모멘텀**: 종목 20일 수익률 − 소속 업종지수 20일 수익률 (F1 일봉 캐시 + C1 업종지수 이력 재사용) — 상위 이탈(+5%p↑)
3. **52주 신고가 근접**: 52주 위치 ≥90% (돌파 관찰 후보)
4. **저점권 반등**: 52주 위치 <30% && 최근 5일 +5%↑

**소음 컷**: 신호 **2개 이상 겹친 종목만** 노출, 최대 5종목. 점수화·가중치 없음(F1 교훈 — 튜닝 금지, 신호 나열만). 신호 0~1개면 섹션 자체를 숨김(억지로 채우지 않음).

**출력**
```
GET /discovery → { date, universe: Int, candidates: [
  {code, name, sector, signals: [{type, detail}], price, changePct} ], caveat }
```
당일 파일 캐시. 후보 풀 시세는 `/quotes` 병렬 패턴(Semaphore) 재사용.

### 슬라이스
- **✅ D1 (Fable, 커밋 2c647e1)** — 유니버스 29종목 + 신호 4종 + 교집합 컷 + `GET /discovery` + DiscoveryTest 10. curl 검증 완료(현대로템 후보 적중). **스펙 편차**: 상대모멘텀 벤치마크는 업종지수 대신 **코스피(0001)** — 세부 Sector→업종지수 매핑이 대분류 1:N 혼재라 오분류 회피.
- **D2 (Sonnet)** — 앱: 브리핑 탭 "지켜볼 후보" 섹션(신호 배지 + 탭→상세, 상세에서 관심 추가는 기존 플로우) iOS+Android. (선택) Slack 아침브리핑에 후보 한 줄.

### 테스트
상대 모멘텀 계산·신고가/저점반등 판정·2신호 교집합 컷·관심종목 제외·빈 결과 각 유닛. 엣지: 바스켓 종목의 일봉 이력 부족(<60일 → 해당 종목 skip), 업종지수 매핑 없는 종목(상대 모멘텀 skip, 다른 신호는 평가).

### 리스크·한계
- 후보 폭이 바스켓 하드코딩에 갇힘 — 신규 섹터 발굴은 못 함. v2 후보: KRX 등락률/거래량 상위 스캔(호출량·소음 재검토 필요). v1은 의도된 제약.
