# 의사결정 기록 (ADR-lite)

주요 선택과 "왜"를 짧게 남긴다. 새 결정은 아래에 덧붙이고, 번복되면 해당 항목에 *(번복: …)* 표기.

## 1. 앱과 데이터 소스 사이에 백엔드를 둔다
- **결정:** 앱은 외부 API(한투/DART/Claude)를 직접 호출하지 않고, 키도 갖지 않는다. 모든 호출은 백엔드 경유.
- **왜:**
  - 한투 앱키 1개를 백엔드가 보관 → **사용자는 한투 계좌 없이도** 시세를 본다(키 공유·중계).
  - Claude/한투 키가 클라이언트에 노출되지 않는다(디컴파일·프록시로 탈취 방지).
  - 같은 종목·시점 시세/분석을 **공유 캐시**로 묶어 호출량·Rate Limit을 제어(N명 → ≈1×).
  - 정기 작업(아침 브리핑·신호 스캔)을 백엔드 스케줄러로 처리.
- **대가:** 서버를 직접 운영해야 함(사용자가 수용).

## 2. 백엔드 = Cloud Run + Ktor (Kotlin)
- **결정:** Cloudflare Workers(TS) 대신 Cloud Run + Ktor.
- **왜:** KMP 앱과 **언어를 Kotlin으로 통일**(컨텍스트 전환·DTO 공유 유리), 배치·DB 붙이기 자유로움.
- **대안:** Workers는 더 가볍지만 TS라 언어가 갈리고 배치/상태 작업에 제약.

## 3. KMP, 단 UI는 네이티브 / 로직만 공유
- **결정:** iOS=SwiftUI, Android=Compose, **비즈니스 로직(네트워킹·모델·로컬DB)만 KMP 공유**. Compose Multiplatform UI 공유는 끔.
- **왜:** 각 OS 네이티브 UX를 살리면서, 반복되는 로직은 한 번만 작성.

## 4. 수급(외인/기관)은 "장후 확정 일별값"을 쓴다
- **결정:** 장중 실시간 추정치 대신 장 마감 후 확정값.
- **왜:** 차별화 기능인 "신호 기반 매수 승률" 통계가 장중 추정치로는 흔들려 **학습 데이터가 오염**된다. 현재가만 준실시간이면 판단 보조엔 충분.

## 5. 종목 검색은 한투 공개 "종목 마스터 파일" 방식
- **결정:** 한투엔 이름검색 API가 없어, 공개 .mst(KOSPI/KOSDAQ) 파일을 받아 메모리 인덱스로 검색.
- **왜:** 인증 불필요·호출비용 0·오프라인 검색 가능. 파일 포맷(고정폭/cp949)은 [kis-api-notes.md](backend/kis-api-notes.md) 참고.

## 6. 캐시는 "필요해질 때" 넣는다
- **결정:** 처음엔 깡통 프록시로 시작, 캐시·공유는 Rate Limit/비용이 실제로 아플 때 추가.
- **왜:** 미리 설계하면 안 쓸 구조 잡느라 시간 낭비. 앱은 백엔드 API만 보므로 캐시는 나중에 넣어도 영향 없음.

## 7. 작업은 vertical slice 단위
- **결정:** 백엔드 1엔드포인트 ↔ 앱 1화면을 end-to-end로 돌려보고 다음으로. Phase 전체를 한 번에 만들지 않음.
- **왜:** 매 단계 "보이는 결과 + 빌드·실행 검증"으로 리스크를 일찍 제거. 백엔드(한투 연동)가 진짜 리스크라 먼저 함.

## 8. 백엔드 아키텍처 = 가벼운 레이어드 + package-by-feature (Phase 2부터 적용)
- **결정:** 지금은 컨벤션만 문서화([architecture.md](backend/architecture.md)), 실제 폴더 재구성은 기능이 늘어나는 Phase 2에. 풀 DDD는 복잡한 도메인(분석/학습)에만 국소 적용.
- **왜:** 기능 2개에 풀 DDD/레이어 분리는 오버엔지니어링. 방향(package-by-feature, 안티커럽션 유지)은 지금 고정하되, 리팩터링 비용은 효용이 생기는 시점으로 미룬다.
- **대안:** 지금 전면 DDD — 효용 대비 ceremony 과다라 보류.

## 9. iOS 배포는 TestFlight (Apple Developer 계정 등록 시)
- **결정:** 외부 배포 시 7일 재서명 대신 TestFlight.
- **왜:** 7일 재서명은 매주 재설치라 비현실적. TestFlight는 외부 테스터 100명까지 링크 설치. Android는 서명된 APK 직접 배포.

## 10. 모델 라우팅 기본값 = Opus는 "하루 기준점"에만 (2026-07-03 재확정)
- **결정:** `DEFAULT_OPUS_TRIGGERS` = {briefing, analysis_initial}. 급변 자동 재생성·수동 새로고침·재료 판정은 Sonnet. env `OPUS_TRIGGERS`로 언제든 재조정.
- **왜:** CLAUDE.md의 "facts 강화로 Sonnet 충분" 결정과 코드 기본값(전부 Opus)이 어긋나 있었다. 재료 판정은 JSON 분류라 판단력 프리미엄이 불필요하고, 수동 새로고침은 연타 가능한 볼륨 트리거(5분 쿨다운도 추가). 판단력이 하루의 기준점을 만드는 곳(브리핑·종목 최초 생성)에만 Opus.
- **대안:** 전부 Opus 유지 — 품질 차이 대비 분석 1회 ~5배 비용이라 기각.

## 11. 요약 블록 한정 환각 가드 + 1회 자동 재생성 (2026-07-03)
- **결정:** Claude 응답의 `### 핵심 요약`에서 facts에 없는 가격류 수치(≥1000, ±5% 허용)가 발견되면 같은 모델로 1회 재생성. 본문 전체 검사·UI 경고(numberWarning)는 계속 안 함(로그만).
- **왜:** 실사고 — 학습 프라이어 주가("53,700원")가 사용자 노출 최상단인 요약에 그대로 나감. 본문 전체 숫자 매칭은 가공·라운드 표현 오탐으로 이미 폐기했지만, 요약은 짧고 facts 수치를 직접 인용하는 블록이라 오탐이 거의 없다. 프롬프트 말미 재강조(FINAL_GUARD)와 이중화.
- **대안:** numberWarning UI 복원 — 앱 변경 필요 + 오탐 시 신뢰 훼손이라 보류(재생성으로도 못 잡으면 재검토).

## 12. 리레이팅 판단은 "룰 감지 + 프레임 전환", 모델 재량 아님 (2026-07-03)
- **결정:** 이익 급변 종목(AI·반도체·방산 등)의 "과거 밴드 기준 만성 고평가 판정" 편향은 ① 연환산 포워드 PER을 facts에 병기하고 ② `RegimeDetector`(룰)가 리레이팅/디레이팅 국면을 판정해 레이블+근거를 facts에 주입, ③ 프롬프트(C11)는 레이블이 있을 때만 해석 프레임을 바꾸는 3단으로 푼다. 레짐 판정을 Claude에게 맡기지 않는다.
- **왜:** "이 종목은 리레이팅이니 좋게 봐라"를 모델 재량에 두면 낙관 환각의 문이 열린다. 감지는 계산(주가vs목표가·목표가 추세·분기 YoY — 전부 우리 데이터), 모델은 프레임만. 신호 2개 미만이면 레이블 자체를 생략해 일반 종목엔 영향 0. 디레이팅 경계도 대칭 구현해 "싸 보이는 함정" 방향 편향도 동시에 막는다.
- **대안:** 성장주 전용 별도 모드(사용자 토글) — 사용자가 종목마다 판단해야 해서 기각. 프롬프트에 "성장주는 관대하게" 일반 규칙 — 전 종목 낙관 편향이라 기각.

## 13. 개발 작업 모델 = 3티어 (Sonnet / Opus / Fable) (2026-07-05)
- **결정:** 코딩 에이전트를 돌리는 모델 정책을 3티어로. **디폴트 Opus.** 가장 복잡하고 정확한 추론이 필요한 작업(프롬프트 설계, 어려운 아키텍처/정합성 판단)은 **Fable.** 아주 단순·기계적인 작업(검증된 패턴 복제, 단순 UI 배선)만 **Sonnet.** 슬라이스 시작 전 스텝+모델 추천→승인.
- **왜:** 기존 "Sonnet 기본, 복잡 시 Opus"는 Fable 등장 전 정책. 판단·설계 실수의 되돌리기 비용이 모델 비용보다 크므로 디폴트를 Opus로 올리고, 진짜 어려운 추론에는 최상위(Fable)를 쓴다. 단순 반복은 Sonnet으로 절감.
- **주의:** 이건 **개발(코딩 에이전트) 모델** 정책이다. 런타임 AI 코멘트 생성 모델(`ModelRouter`/`DEFAULT_OPUS_TRIGGERS`, #10)과는 **별개 축**이다 — 백엔드 Anthropic REST는 현재 Sonnet/Opus만 연결돼 있고, Fable을 런타임에 쓰려면 라우터에 별도 배선이 필요하다.

## 14. SENSITIVITY 부호는 실측이 논리를 이긴다 — usdkrw·copper 지표 차원 교정 (2026-07-11, D2)
- **결정:** 2년 실측 검증(D1, [sensitivity-validation-2026-07.md](sensitivity-validation-2026-07.md)) 결과로 SENSITIVITY를 교정. **usdkrw 전 6칸 +1→−1**("원화 약세=수출 우호" → "환율 급등=외국인 이탈·리스크오프 신호"), **copper 전 3칸 −1→+1**("원가 부담" → "경기 선행 신호, Dr. Copper"). crude·usdjpy는 실측 무근거(무유의)지만 반증도 아니라서 유지. nasdaq(+1)·rate3y(−1)는 실측 강지지로 유지.
- **왜:** 이 테이블의 의미는 "오늘 지표 등락 → 오늘/내일 종목 방향"인데, usdkrw·copper의 기존 부호는 일별 시계에서 실측과 유의하게 반대였다(usdkrw는 6/6 그룹 방향 일치 — 개별 셀이 아니라 지표 차원 구조). 수출 채산성·원가 부담은 분기 실적 시계의 논리라 일별 신호로는 자금 흐름·경기 신호에 압도된다. 교정은 셀 단위가 아니라 **지표 단위로 통일** — 셀만 뒤집으면 같은 지표가 그룹마다 반대 방향인 비일관 테이블이 된다(조선·방산 usdkrw는 개별 유의 아님이지만 방향 일치 + 지표 차원 논리로 포함).
- **회귀 방지:** `MacroSignalTest`에 usdkrw=−1·copper=+1 고정 테스트 추가 — 논리적 직관("수출주는 원화 약세 수혜")으로 되돌리려는 미래의 수정을 막는다.
- **대안:** CONTRADICTED 셀만 반전(비일관 테이블이라 기각), usdkrw 제거(신호 자체는 유의해서 방향만 고치면 정보가 됨 — 기각), crude·usdjpy도 제거(반증이 아닌 무유의는 국면 의존일 수 있어 유지).

## 15. Discovery 신고가근접 신호 제거 — 실측 반증 (2026-07-14, ②-2b)
- **결정:** 후보 발굴(D1)의 가격 신호에서 **신고가근접(52주 위치 ≥90%)을 제거**. 상대모멘텀(+5%p 컷)·저점반등은 유지, 컷 값도 유지(그리드 {+3,+7} 비교에서 +5 열위 아님 — 튜닝 금지 원칙).
- **왜:** ②-2b 실측([discovery-analog-validation-2026-07.md](discovery-analog-validation-2026-07.md), peer 37종목×750봉, n=642)에서 신고가근접 발화 후 20거래일 코스피 대비 초과수익 **−1.32%p·승률 −4.0%p** — baseline보다 명확히 열위. "돌파 관찰"이라는 설계 의도와 달리 실제로는 단기 과열 꼭지를 잡는 신호였고, 교집합(2신호) 컷 전체를 baseline 아래(−0.49%p)로 오염시키던 주범. 제거 후 가격 교집합(상대모멘텀∧저점반등)은 n=43·20일 +0.58%p·승률 +9.6%p로 회복.
- **회귀 방지:** `DiscoveryTest`에 신고가근접 미발화 고정 테스트. 재도입하려면 `GET /discovery-validation` 재실측으로 근거 갱신이 선행 조건.
- **대안:** 유지+caveat만(사용자에게 열위 신호를 계속 노출할 이유 없음 — 기각), MIN_SIGNALS 3으로 상향(후보가 사실상 0이 됨 — 기각), 컷 95%로 강화(사전 지정 그리드 밖 튜닝 — 기각).
